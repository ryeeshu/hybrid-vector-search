Heterogeneous CPU–GPU Graph-Based Vector Search with Memory-Aware Execution

Team Members: R Yeeshu Dhurandhar (rdhurand), Christian Yu (cjyu)

Project Website: https://ryeeshu.github.io/hybrid-vector-search/

1. Summary

We plan to build a hybrid CPU–GPU engine for graph-based Approximate Nearest-Neighbor (ANN) search, focusing on datasets that cannot fit entirely in GPU memory. We will investigate how parallel query processing, efficient CPU–GPU communication, batching, and overlapping computation with data transfers can improve search performance. Our implementation will use C++ multithreading and SIMD on the CPU, along with CUDA for parallel computation on the GPU.

2. Background

Vector similarity search is widely used in applications such as recommendation systems, image retrieval, and semantic search. Each item in a dataset is represented as a high-dimensional vector, and given a query vector, the goal is to find the most similar vectors in the dataset.

A straightforward solution is to compute the distance between the query and every vector. Although these distance calculations are highly parallelizable, examining the entire dataset can become expensive as its size increases.

Approximate Nearest-Neighbor (ANN) algorithms reduce this cost by examining only a subset of the vectors. In graph-based ANN algorithms, such as Hierarchical Navigable Small World (HNSW), each vector is represented as a vertex connected to other nearby vectors. Starting from an entry vertex, the search repeatedly explores promising neighbors until it finds a set of approximate nearest neighbors.

Unlike brute-force search, graph traversal has dependencies because the next vertices to explore are determined by the results of previous steps. Different queries may also explore different numbers of vertices, making the workload irregular and difficult to distribute efficiently.

GPUs can accelerate distance calculations across many candidate vectors, but GPU memory is limited. For large datasets, storing both the graph and all the original vectors on the GPU may not be possible. Transferring data between CPU and GPU memory also introduces overhead, especially when each graph-search iteration requires only a small amount of computation.

We plan to address these problems by keeping the complete graph and vector dataset in CPU memory while using the GPU to process batches of candidate vectors. The CPU will manage graph traversal and identify candidates, while the GPU will perform parallel distance calculations. We will investigate how to organize and schedule this work so that the GPU has enough computation to justify the communication cost.

The proposed execution flow is:

  1. The CPU maintains the search frontier for each query and identifies the next candidate vertices.
  2. Candidate vectors from multiple queries are grouped into batches and transferred to the GPU.
  3. CUDA kernels compute distances between the candidate vectors and their corresponding queries.
  4. The results are returned to the CPU, which updates each query's search frontier.
  5. The process continues until the searches finish.

We will progressively optimize this design to reduce communication overhead and improve CPU and GPU utilization.

3. The Challenge

The main challenge is that graph-based ANN search does not provide the same regular, independent work as brute-force vector search. Although distance calculations can execute in parallel, graph traversal introduces dependencies and irregular memory accesses. We want to investigate how to expose enough parallelism to use the GPU efficiently without introducing excessive communication or synchronization overhead.

Irregular graph traversal and workload imbalance. Each query follows a different path through the graph, and the number of candidates discovered at each step varies. Some queries may finish quickly, while others require many more expansions. Assigning a fixed amount of GPU work to each query can therefore lead to poor utilization. We plan to explore batching candidates from multiple queries and distributing this work across CUDA threads. We will also examine how batch size affects load balance, throughput, and latency.

CPU–GPU communication overhead. Unlike conventional GPU workloads that perform many operations on the same data, graph search can require frequent communication between the CPU and GPU. Each iteration depends on results from earlier iterations, so transferring only a few vectors at a time may cost more than the computation itself. We want to study how much communication can be reduced or hidden through batching and pipelined execution.

Limited GPU memory and data locality. The full dataset may be larger than available GPU memory, requiring candidate vectors to be fetched from host memory. Graph traversal can access vectors scattered throughout the dataset, resulting in poor locality and unpredictable transfers. We plan to implement a bounded GPU-memory staging system and investigate how the available device memory affects performance. If time permits, we will explore caching frequently accessed vectors on the GPU to reduce repeated transfers.

Overlapping computation and communication. In a naive implementation, the CPU discovers candidates, waits for their transfer and GPU computation, and then resumes traversal. This leaves one or both processors idle at different points. We plan to investigate asynchronous transfers and multiple CUDA streams so that the CPU can prepare future work while the GPU processes existing batches. The difficulty is coordinating these operations while respecting the dependencies of each search and avoiding unnecessary synchronization.

Search quality versus performance. Since ANN search is approximate, changing the number of candidates explored or the order in which they are processed may affect the quality of the results. We will evaluate search accuracy using recall@k and compare execution strategies at similar recall levels. This will help distinguish genuine performance improvements from approaches that simply perform less search work.

Through this project, we hope to better understand how irregular, dependency-heavy workloads can be mapped efficiently onto heterogeneous parallel hardware, and how memory placement, communication, and scheduling decisions affect overall performance.

4. Resources

We plan to implement the engine primarily in C++ and CUDA, using the course's GHC machines equipped with NVIDIA RTX 2080 GPUs. We will use CPU multithreading for concurrent graph traversal and SIMD instructions where appropriate for CPU distance calculations. CUDA kernels will perform batched candidate-distance computations, while CUDA streams and pinned host-memory buffers will be used to investigate asynchronous transfers and communication-computation overlap.

We plan to use Faiss to construct the HNSW index and extract its graph connections for our own search implementation. We will verify the graph extraction and search interface during the first week. We will implement our own search traversal, candidate batching, CUDA computation, and CPU–GPU execution pipeline rather than rely on an existing ANN library for the main search operation.

We plan to begin with the SIFT1M benchmark, which contains one million 128-dimensional vectors, along with query vectors and ground-truth nearest-neighbor results. We will also use controlled synthetic workloads to vary dataset size, query concurrency, and access patterns.

Since SIFT1M fits within GPU memory, we will initially enforce a configurable GPU-memory budget to study out-of-core behavior. If resources and index-construction time permit, we will also evaluate a larger dataset whose memory footprint genuinely exceeds the available GPU memory.

Our primary references will be the BANG paper on CPU–GPU graph-based ANN search, NVIDIA's CAGRA graph-search design, and the CUDA programming and optimization documentation.

5. Goals and Deliverables

Our main goal is to develop a working CPU–GPU graph-based ANN engine and evaluate how different execution strategies affect search throughput, latency, communication overhead, and hardware utilization.

5.1 What We Plan to Achieve

1. CPU-based graph-search implementation

We will implement a graph-based ANN search engine in C++ that maintains candidate frontiers, explores graph neighbors, computes distances, and returns approximate nearest neighbors. We will support multiple concurrent queries using CPU multithreading and investigate SIMD acceleration for distance calculations. This implementation will serve as our CPU-only performance baseline.

2. Basic hybrid CPU–GPU execution

We will implement a hybrid version in which the CPU controls graph traversal and the GPU computes distances for candidate vectors. Our initial implementation will perform candidate transfers and GPU computation in a straightforward, synchronized manner. This will provide a baseline for measuring communication and synchronization overhead.

3. Parallel batching of graph-search workloads

We will develop a batching mechanism that combines candidates from multiple independent queries into larger GPU workloads. Each query will maintain its own search state, while the shared GPU execution path processes candidate vectors in parallel. We will investigate different batch sizes and measure their effects on GPU utilization, search throughput, and query latency.

4. Memory-limited CPU–GPU execution

We will vary the available GPU-memory budget to investigate how buffer capacity, batch size, and the number of concurrent transfers affect performance. If time permits, we will also introduce GPU-resident caching to study how data reuse and memory placement can reduce transfer overhead.

5. Pipelined execution and communication overlap

We will implement a pipelined execution strategy using asynchronous CUDA operations and multiple buffers. The goal is to overlap CPU graph traversal, data transfers, and GPU computation across independent query batches wherever dependencies allow. We will compare this implementation against the synchronized hybrid baseline to determine whether overlapping these operations improves performance.

6. Performance evaluation

We will compare the following execution strategies:

  • CPU-only graph search.
  • Basic hybrid CPU–GPU search with synchronized transfers.
  • Hybrid search with batched candidate processing.
  • Hybrid search with asynchronous, pipelined execution.

We will evaluate performance across different dataset sizes, query batch sizes, search parameters, and GPU-memory budgets.

Our primary metrics will be queries per second, average and tail query latency, recall@k, CPU–GPU data-transfer time and volume, and the time spent in different execution stages. We will also use CPU and GPU profiling tools to investigate memory bandwidth, kernel execution, synchronization overhead, and hardware utilization.

We hope to achieve a meaningful throughput improvement over the basic hybrid implementation, particularly for workloads with many concurrent queries. As an initial performance target, we would like to investigate whether batching and pipelining can provide at least a 1.5× throughput improvement on suitable batch-heavy workloads. This is a tentative goal based on the opportunity to reduce repeated kernel-launch overhead and overlap otherwise idle periods; the actual benefit will depend on the hardware and workload. We will report and analyze the results even if the improvement is smaller or the CPU-only implementation performs better.

5.2 What We Hope to Achieve

1. GPU-resident vector caching

If the main implementation is completed ahead of schedule, we would like to introduce a cache for selected vectors in GPU memory. Instead of transferring every candidate vector whenever it is needed, the engine could reuse vectors that are already resident. We would compare simple caching policies and study how cache size and query locality affect transfer volume and performance.

2. More parallel graph traversal on the GPU

We would also like to explore moving some graph-search operations, such as candidate selection or frontier expansion, onto the GPU. This could reduce the need to return intermediate results to the CPU after every iteration and expose additional parallelism within individual searches. However, it would require managing dynamic search state and synchronization on the GPU, so we consider it an ambitious extension rather than a required feature.

3. Adaptive CPU–GPU Workload Scheduling

If the main hybrid search engine is completed ahead of schedule, we would like to explore an adaptive scheduling strategy that decides whether candidate-distance computations should execute on the CPU or GPU. Instead of always sending candidates to the GPU, the scheduler would consider factors such as batch size, GPU availability, data-transfer overhead, and whether the required vectors are already present in GPU memory.

We would first implement a simple threshold-based scheduling policy and then investigate a workload-aware policy using measured execution costs. We would compare these approaches against CPU-only and GPU-only candidate processing under different query loads, measuring throughput, average and tail latency, and communication overhead. Our goal would be to identify when using both processors is beneficial and when the overhead of GPU execution outweighs its advantages.

5.3 Goals If Progress Is Slower Than Expected

If implementation or integration takes longer than expected, we will prioritize completing the CPU-only engine, the basic hybrid execution path, and multi-query GPU batching.

We would simplify the asynchronous pipeline if necessary and concentrate on comparing the working implementations thoroughly, including identifying communication and synchronization bottlenecks. GPU-resident caching and GPU-managed graph traversal would remain optional.

5.4 Expected Experimental Findings

In addition to measuring performance improvements, we want to answer several questions:

  • At what query batch sizes does GPU acceleration become beneficial compared with CPU-only search?
  • How much does combining graph-search work from multiple queries improve GPU utilization?
  • How much time is spent computing distances versus transferring data and waiting for synchronization?
  • Under what conditions does overlapping CPU work, transfers, and GPU execution improve throughput?
  • How does reducing the available GPU-memory budget affect execution time?
  • How does the amount of graph exploration affect the trade-off between search accuracy and performance?

We expect different execution strategies to perform better under different workloads, rather than one implementation being optimal in every case.

At the poster session, we plan to present the system architecture, performance graphs, and a breakdown of the main bottlenecks. If time permits, we may also provide a small demonstration that runs the same query workload using different execution modes.

6. Platform Choice

We chose a heterogeneous CPU–GPU platform because the two architectures have different strengths that are relevant to graph-based ANN search.

The CPU is well suited for managing control-heavy operations such as graph traversal, maintaining candidate frontiers, and making decisions based on previously computed results. Multithreading can also allow multiple independent queries to progress concurrently.

The GPU is well suited for performing the same numerical operation across many candidate vectors. By combining candidate work from several queries, we aim to create sufficiently large batches to make effective use of CUDA's parallel execution resources and memory bandwidth.

The main difficulty is that the CPU and GPU have separate memory spaces, and data movement between them can be expensive. This makes our chosen platform useful for studying the interaction between computation, communication, data locality, and synchronization.

C++ and CUDA provide direct control over memory allocation, CPU threads, GPU kernels, and asynchronous operations, allowing us to experiment with different parallel execution strategies and measure their overheads.
